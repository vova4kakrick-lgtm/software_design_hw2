# ПОС — преподавательская оценка студентов

Консольное приложение: студенты, рубрикатор (критерии), оценки, итог по весам, экспорт итогов в JSON.
.NET 10, DDD + Clean Architecture + паттерны GoF.

## Запуск

```bash
dotnet run --project src/Pos.Cli            # интерактивное меню, данные в ./data
dotnet run --project src/Pos.Cli -- --demo  # сквозной сценарий: критерии → студенты → оценки → итог → экспорт
dotnet test                                 # юнит-тесты
```

## Архитектура: Clean Architecture

```
Pos.Cli ────────────────► Pos.Application ──► Pos.Domain
   │                            ▲                  ▲
   └──► Pos.Infrastructure ─────┴──────────────────┘
```

Зависимости направлены только внутрь, это проверяет компилятор через ссылки между проектами:
Domain не ссылается ни на что, Application — только на Domain, Infrastructure реализует порты из Domain
(`IStudentRepository`, `IRubricRepository`) и Application (`ITotalsExporter`). `Pos.Cli` — внешний слой и
composition root: только он знает конкретные классы инфраструктуры и собирает граф в DI.

| Слой | Проект | Что внутри |
|---|---|---|
| Domain | `Pos.Domain` | `Model/` — сущности и VO; `Repositories/` — порты хранения; `Services/Totals/` — доменный сервис итога и стратегии |
| Application | `Pos.Application` | Сценарии: студенты, рубрикатор, оценки, итоги. Порт `ITotalsExporter`. Ошибки домена переводятся в `UseCaseException` |
| Infrastructure | `Pos.Infrastructure` | JSON-репозитории, маппинг DTO ↔ домен, экспорт итогов в JSON |
| Presentation | `Pos.Cli` | Консольные меню, демо, `CompositionRoot` (DI-контейнер `Microsoft.Extensions.DependencyInjection`) |

Домен не знает про файлы, JSON и консоль — и даже про то, как правило итога подписано на экране: русские
названия правил живут в `Pos.Cli` (`ViewPrinter.RuleName`), а в экспорт уходит машинный код правила (`strict`/`current`).
UI вызывает только сценарии Application; нарушения доменных правил приходят к нему как `UseCaseException`,
а ошибки чтения файлов — как `IOException`/`InvalidDataException`. CLI в файлы сам не ходит: экспорт
возвращает `ExportResult` (куда выгружено + что выгружено).

## Карта DDD

| Термин предметной области | В коде | Тип |
|---|---|---|
| студент | `Student` | Entity, корень агрегата (владеет своими оценками) |
| рубрикатор | `Rubric` | Корень агрегата (владеет критериями). Курс один, поэтому и рубрикатор один — отдельный `RubricId` не нужен; при нескольких курсах он появится вместе с `CourseId` |
| критерий | `Criterion` | Entity внутри `Rubric` (идентичность — `CriterionId`) |
| оценка | `Evaluation` | Value Object: факт «балл по критерию», меняется только заменой целиком |
| балл, вес, номера | `Score`, `Weight`, `StudentId`, `CriterionId` | Value Object |
| итог | `TotalCalculator` → `StudentTotal` | Domain Service: правило касается и студента, и рубрикатора |

**Entity и VO на примере.** Два студента с одинаковым ФИО — разные студенты, потому что у них разные номера `StudentId` (Entity).
Два `Score(7)` — одно и то же значение (VO, `record`). Поэтому исправить оценку значит заменить её новым `Evaluation`, а не изменить поле.

**Инварианты:**
- балл в пределах критерия: `Score` не бывает отрицательным, верхнюю границу проверяет `Criterion.EnsureAccepts`;
- критерий корректен: название не пустое, `max_score > 0`, вес `0 < w ≤ 1000` (веса относительные, граница гарантирует, что сумма весов не переполнит `decimal`);
- оценка только по критерию из рубрикатора: конструктор `Evaluation` — `internal`, создать оценку можно только через `Rubric.Evaluate`;
- одна оценка на критерий у студента: `Student.Record`;
- итог не хранится, а каждый раз считается `TotalCalculator` из текущих оценок и рубрикатора.

**Repository:** порты `IStudentRepository` и `IRubricRepository` лежат в домене, реализации на JSON — в Infrastructure.

## Паттерны GoF

По одному паттерну из каждой группы — каждый закрывает конкретную боль.

| Группа | Паттерн | Где | Какую боль закрывает |
|---|---|---|---|
| Порождающий | Фабрика | `Rubric.Evaluate` (конструктор `Evaluation` — `internal`) | Единая точка создания оценки с инвариантами. Без неё проверку «критерий есть в рубрикаторе» и «балл ≤ max» пришлось бы повторять в каждом месте, где появляется оценка: выставление, исправление, загрузка из файла. Здесь обойти правило нельзя — другого способа получить `Evaluation` нет |
| Структурный | Decorator | `Domain/Services/Totals/RoundedTotalStrategy` | Модификатор подсчёта не размазан по UI и экспорту. На экране итог точный, в ведомость уходит целый — округление навешивается поверх *любого* правила в одном месте. Без декоратора пришлось бы либо добавлять флаг `round` в каждую стратегию, либо округлять в экспортере/консоли (то есть знание о правиле итога утекло бы во внешние слои) |
| Поведенческий | Strategy | `ITotalStrategy`: `StrictTotalStrategy`, `CurrentTotalStrategy` | Правило итога сменное: «нет оценки = 0» (финальная ведомость) или «только выставленные» (промежуточный срез в середине семестра). `TotalCalculator` собирает строки итога и от правила не зависит; новое правило — новый класс, без правки сервиса |

Стратегия и декоратор собираются в одном месте — `Application/Totals/TotalRuleFactory`: выбор пользователя
(правило + «округлять») превращается в готовый `ITotalStrategy`, базовые стратегии приходят из DI.
Это вспомогательный класс сценария итогов, отдельным GoF-паттерном мы его не считаем.

## Решения

- **Номера выдаются автоматически:** студенту — репозиторий (`IStudentRepository.NextId`), критерию — сам рубрикатор. Критерии не удаляются, поэтому при загрузке номера восстанавливаются по порядку.
- **Комментарий к оценке необязателен**, дата ставится автоматически.
- **`JsonStudentRepository` читает рубрикатор.** При загрузке оценки восстанавливаются через `Rubric.Evaluate`, поэтому вручную испорченный файл (например, 12 из 10) не загрузится. Альтернатива — публичный конструктор `Evaluation` — позволила бы обойти правило из любого места кода.
- **Итог по шкале 0–10:** взвешенная доля набранного от максимума. Веса относительные: `0.6/0.4` и `3/2` дают одинаковый итог.
